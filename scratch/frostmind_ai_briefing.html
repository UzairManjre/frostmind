FROSTMIND · 01 · system

What FROSTMIND is

An ESP32-S3 sensor node watches temperature, humidity and door state on a refrigerated shipment, decides when something's wrong, and can act — firing an IR command at the cooling unit — with no human in the loop, then explains itself to one afterward.

Why this shape: the ESP32 has no internet radio, so a phone acts as a Bluetooth-to-HTTPS bridge — which is also why "always-on background connectivity" has a hard ceiling. A browser tab can't run truly in the background; that limit is disclosed honestly rather than papered over. Everything downstream of /ingest is where the AI actually lives — precisely four AI/reasoning components, plus the one deterministic on-device rule that closes the loop today.

Photo slot — add before presentingThe ESP32-S3 rig on the bench (sensor + IR transmitter + phone), or the admin dashboard mid-alert.

FROSTMIND · 02 · design philosophy

Stage the models to the data you actually have

The single biggest judgment call to defend: no model was trained before there was data to train it on — and that's said out loud, not hidden. Five stages, and exactly where each one really stands today:

STAGE 0

Threshold rule

Live

Deterministic on-device rate-of-change + setpoint check — firing real IR commands today.

STAGE 1

Isolation Forest

Built · not active

Trained & validated on 4 benchmark datasets. Not yet pointed at live telemetry — see next slide for exactly why.

STAGE 2

Root-cause classifier

Not built

Needs an INA219 power-draw sensor that hasn't been sourced. A hardware gap, not a coding one.

STAGE 3

Arrhenius kinetics

Live

Physics-based — needs zero training data. Computing real numbers on every reading.

STAGE 4

LLM reasoning

Live

Ollama-hosted, local. Running in production ahead of the original plan's own schedule.

"The instrumentation had to exist before the model could, because the model needs data only the instrumentation produces — that's not a missing feature, that's the correct order of operations."
Say this plainly — Stage 1 is genuinely trained and evaluated, just not yet wired to live data, and that distinction is worth being precise about if asked.

FROSTMIND · 03 · model 1

Anomaly detection — Isolation Forest

HandlesFlagging that a reading pattern is anomalous relative to normal operation, from live rolling sensor stats. Complements the threshold rule with earlier, subtler detection — it does not replace it, and it does not decide what action to take.

sklearn.ensemble.IsolationForest, contamination=0.02, trained only on rows/sessions labeled normal — the model never sees an anomaly label during training. Features: rolling mean temp, rolling volatility, rate of change, and door-open duration, over a 10-reading window.

100% recall isn't proof of a hard problem solved

The milk dataset's ALERTA label looks like it was originally assigned by a simple temperature threshold — an easy target for anything that can see rolling temperature stats.

82.3% is a ceiling, not a preview

The supervised row proves the sensor features genuinely predict silent failure (top predictors: temp_max_c, transit_days, door_opens, rh_std) — but it uses labels FROSTMIND won't have on day one.

Why it's off #1 — feature-schema mismatch

The shipment-level models use 22 session-aggregate features over a whole completed trip — not the per-reading stream /ingest receives every ~2 seconds. A straightforward input-shape error waiting to happen.

Why it's off #2 — domain mismatch

Even the rolling-window models are calibrated to one narrow temperature band. A model trained on milk (0–15°C) would flag nearly every −18°C frozen-food reading as anomalous, by construction — confidently wrong beats not run, only when "confidently wrong" isn't the real behavior.

Current real status app/ml.py checks at import time whether models/model1_isolation_forest_frostmind.pkl exists. It doesn't yet — score_with_model1() is a documented no-op returning (None, None). The ESP32's on-device threshold rule is the system's real, live detection mechanism today — not a placeholder pretending to be something fancier.

FROSTMIND · 04 · model 2

Root-cause classification — deliberately not built

Would handleExplaining why an anomaly happened — compressor fault vs. a door left open vs. a power loss — instead of just flagging that something's wrong. A second stage on top of Model 1's detection, not a replacement for it.

What it would do: given an anomaly Model 1 flags, classify why — a failing compressor, a door left open, a power interruption — instead of just "something is wrong."

Explicitly deferred hardware, not a scripting gap: no training script, no dataset, no stub model exists for Model 2, and none should — a fake classifier without the signal it needs would be a worse look than an honest "not yet."

If asked: "why not at least simulate this one too" The other models had real or credible-simulated public datasets to validate against. No comparable public dataset pairs AC power-draw fault signatures with cold-chain outcomes — simulating it convincingly would mean fabricating the one thing that makes it a legitimate model, so it was left undone rather than faked.

FROSTMIND · 05 · model 3

Shelf-life kinetics — Arrhenius model

HandlesConverting a shipment's full temperature-exposure history into one number per product category: percent of shelf life already consumed, and hours remaining at the current temperature.

Worth stating plainly: this is not machine learning. It's an established chemical-kinetics model — chosen because it needs zero training data and is fully explainable, both real advantages where "why did it say that" needs a real answer. Warmer storage speeds up degradation; this model integrates that effect over the shipment's actual exposure history instead of just watching a single temperature threshold.

Worked example — real output, run just now A vaccine shipment rated 4,320h (~6 months) at 5°C, held there for 48h except a 6h excursion to 12°C: 
48h exposure, 6h @ 12C
-> 1.31% shelf life consumed
Remaining at 5.0C: 4263.5h
A number a threshold rule can't produce — it quantifies how much a specific excursion actually cost this specific product.

FROSTMIND · 06 · llm orchestration

Local reasoning layer — Ollama, zero cloud dependency

HandlesTurning the other three models' structured output into a plain-English assessment, a recommended action, and — on demand — a full incident narrative for a human reader. Never a detection or control decision itself.

Models 0/1/3 are precise but mute — numbers and booleans, not something a human can act on quickly. The LLM's only job is turning structured output that already exists into plain-English judgment. It is not used for the numerical reasoning those models already do correctly.

Stack: hf.co/unsloth/gemma-4-E4B-it-qat-GGUF:UD-Q4_K_XL — a QAT-quantized instruction-tuned Gemma, chosen over generic post-training quantization for more reliable structured JSON output, running fully local on Ollama (localhost:11434).

The one hard boundary Neither role ever fires an IR command or touches device/shipment control state. LLM output is read-only explanation surfaced to a human. The deterministic path — today the ESP32's on-device rule, later Model 1 — stays the only thing that can trigger a physical action. An LLM is materially less predictable than a validated threshold, and a bad demo answer in a UI panel is a completely different failure class from the wrong physical command firing at a real refrigeration unit.

Timeout is 45s, not a generic 30s — a real cold-start (Ollama had unloaded the model while idle) measured ~25s (17s load + 8s inference). No user waits on a background task, so there's no cost to giving it real margin. Background tasks also run after the HTTP response and the request's DB session is already closed, so the task takes a plain alert_id and opens its own session — passing the ORM objects directly would raise DetachedInstanceError the moment they're touched.

FROSTMIND · 07 · on-device intelligence

The threshold rule, and a constraint-driven AC-pairing trick

The live detection rule (Model 0)

rateOfChange = least-squares slope of last 6 temp samples   (°C/min)
tempAlert    = |rateOfChange| > 3.0  OR  |temp − setpoint| > 3.0°C
doorAlert    = door open longer than 60 seconds
alert        = tempAlert OR doorAlert   → fires IR: power-on, cool, fan-high, 5-min cooldown

No IRDB. No LIRC. No TSOP. IR is transmit-only.

A permanent hardware constraint, not a caveat to fix later. So the AC-pairing algorithm uses the AC's own thermal response as its feedback signal — closing the loop through the physical environment instead of a decoded IR frame.

Curated shortlist, not the whole story

~20 common regional AC-brand protocol names are tried first purely to shorten expected pairing time — every one of the 65 protocols the IR library supports is still tried eventually if nothing curated confirms.

The heartbeat

Every 5 minutes, independent of any alert, the last commanded AC state is unconditionally re-sent — the only mitigation available, with no receiver, for a missed send or an unknown real AC state.

Photo slot — the strongest evidenceVideo or photo of the AC visibly reacting to a command FROSTMIND generated itself — closed-loop proof, and not simulated.

Q — Is any of this actually machine learning, or is it all rules?

One trained ML model exists (Isolation Forest), validated on real benchmark data — it's just correctly not switched on against live data yet, for stated reasons. What's live and intervening today is a deterministic rule, by design, because it's what generates the data the ML model needs.

Q — Why not a cloud LLM API instead?

Zero cloud dependency was deliberate: no data leaves the device, no per-call cost, no network dependency for a system that has to work in a truck. A local quantized model is less capable but sufficient for the explanation task it's actually assigned.

Q — What happens if the LLM gives a bad answer?

Nothing physical. It cannot fire a command — see the hard boundary on the LLM slide.

Q — How do you know the AC-pairing algorithm found the right protocol?

It doesn't claim to find the true remote protocol — only one whose commands produce the right physical effect on this specific AC, verified twice (cool trend on power-on, reversal on power-off). For control purposes, that's the property that actually matters.
